# 代码巡检规则

## 何时使用

用户要求"巡检/体检/看风险/评估这段代码怎么样/准备合并前检查"时，先读本技能；
需要逐项核对时再读 `references/checklist.md`（渐进披露：这里只给维度，细节在 references）。

## 检查维度（按优先级）

1. **安全**：注入面（shell/SQL/路径拼接）、凭据硬编码、危险默认（调试开关、宽权限）、
   不可信输入直进执行链。
2. **可维护性**：重复逻辑、超长函数/文件、隐式全局状态、错误吞掉（空 catch）、
   TODO/FIXME 堆积（`audit_collect` 的扫描结果直接映射到这一维）。
3. **测试**：新改动有没有对应测试、测试是否只覆盖 happy path、fixture 是否随代码漂移。
   有测试目录时派发 `coverage-analyst` 子代理做专项。
4. **变更面**：最近改动的文件按"改动行数 × 风险维度"排序，优先看高改动 + 高风险的文件。

## 严重度判定

- **高**：可导致数据损坏/凭据泄露/远程执行，或生产路径必现的功能错误。
- **中**：特定输入下出错、测试缺口覆盖核心路径、明显的错误处理缺失。
- **低**：风格不一致、命名、日志噪音、可读性。

## 报告纪律

- 先事实后判断；每条风险要能定位到 `path:line`。
- 同一根因只报一次，把受影响位置列在"位置"列。
- 覆盖率结论必须来自 `coverage-analyst` 的实际检索，不能凭文件名猜。
